# Diagram types, definitions and overrides

Every maintained diagram has a persistent definition in `config.yaml` (`diagrams.<name>`) and an output file
in `output.dir`. Definitions carry the type, description, scope, UMLFlow's inferred scope, and your overrides
(see [configuration.md](configuration.md)).

## Use Case (`usecase`)

*What it shows:* actors and the capabilities (use cases) they trigger, inside a system boundary.

*How it is derived:* every **entry point** becomes a use case — HTTP routes (NestJS/Express/Spring/FastAPI/
Flask/Django/Gin/net/http…), event/message listeners, scheduled jobs, CLI commands, and public methods of
controller-like components. Names come from `semantics.yaml` (declared or inferred), otherwise from the
operation name and route ("create" + `POST /orders` → "Create Order", marked inferred). Actors come from
declarations/answers; otherwise the use case is attached to **Unknown actor** and a question is raised.
Functions that are not entry points never become use cases.

*Mermaid:* rendered as a `flowchart LR` (Mermaid has no native use case diagram) — actors as rounded nodes,
use cases as ellipses in a `System` subgraph, `overrides.groups` as nested subgraphs, `relationships` with
`kind: include | extend | generalize`.

## Sequence (`sequence`)

*What it shows:* one block per **flow**: actor → entry point → components → data stores, in call order.

*How it is derived:* from each entry operation, resolved interactions are walked depth-first (cycle-safe,
bounded by `scope.depth` / `analysis.maxCallDepth`). Participants are **components** (controllers, services,
repositories, gateways, modules, external packages), never functions. Private self-calls are inlined; `model`
and `utility` roles are hidden; calls into components outside the scope are cut with their subtrees. Data
access (`Repository<Order>`, Spring Data, `prisma.order.*`, `User.objects`) appears as a message to a
database participant labelled with the access mode. Reply arrows are shown for the first level only.

*Interactions are resolved deterministically* through constructor/field injection types, typed parameters,
imports, same-package names and route registrations; name-based fallbacks (`orderService` → `OrderService`)
are marked inferred. Calls on the result of another call (`repo.find().then()`) are never attributed.

## ERD (`erd`)

*What it shows:* entities with attributes (PK/FK/UK, types, nullability), relations with cardinality.

*Sources:* SQL DDL (`CREATE TABLE`, inline/`FOREIGN KEY`/`ALTER TABLE … ADD FOREIGN KEY`), Prisma schema,
TypeORM decorators, JPA/Jakarta annotations, SQLAlchemy `Column`/`relationship`, Django `models.*Field`,
GORM structs. Entities describing the same table (e.g. `orders` in a migration and `@Entity('orders') Order`)
are merged into one, keeping the domain name. One-to-many relations are normalised to many-to-one from the
FK side; entities referenced but never defined are shown as stubs marked unknown.

## Output files

```markdown
# Login Flow

> User login and authentication flow

_Generated by UMLFlow … the code is the source of truth …_

<!-- UMLFLOW GENERATED BEGIN — do not edit inside this block; run `umlflow update` -->
```mermaid
sequenceDiagram
  …
  %% UMLFLOW MANUAL BEGIN
  Note over auth_controller: anything you add here survives regeneration
  %% UMLFLOW MANUAL END
```

**Analysis notes**

- ❓ 1 flow(s) start from an unknown actor. …
<!-- UMLFLOW GENERATED END -->

<!-- UMLFLOW MANUAL BEGIN — your notes below are preserved -->
Your prose.
<!-- UMLFLOW MANUAL END -->
```

Regeneration replaces only the generated block; the in-diagram manual section is re-inserted, and everything
outside the block is left untouched. Files without markers are never destroyed (the block is appended).
`output.format: mmd` writes bare `.mmd` files with `%% UMLFLOW GENERATED BEGIN/END` markers.

## Uncertainty in diagrams

| Marker | Meaning |
|---|---|
| `label ?` | inferred (naming heuristic, derived name) |
| `label ??` / `Unknown actor` | unknown — answer `umlflow semantic questions` or declare |
| dotted association | actor–use case link that is not declared/deterministic |
| Analysis notes | counts of inferred/unknown facts and unresolved calls |

## Adding a diagram

```bash
umlflow generate --type sequence --name checkout --about "checkout orders payment"
umlflow generate --type erd --name billing-erd --entities Invoice Payment
umlflow generate --type usecase --name admin --include src/admin
```

Or write the definition by hand in `config.yaml` and run `umlflow update <name>`.
